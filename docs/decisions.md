# 关键决定

只加不删。每条几行：决定了什么、为什么，以及放弃了哪些选项。

## 2026-11-16 在同一仓库里分三层重做底层，数据全部保留

- 决定：重新划成伙伴本体、生活世界、呈现与连接三层；上层只能通过 contracts 访问下层，由自动检查守住。先立新骨架，再从底层往上一块块重写，写完一块删掉对应的旧代码，每一步都能跑、能发版。代码留在原仓库，按新项目管理（行为清单、迁移与回退演练、分阶段、评审点）。
- 为什么：Core 反向引用上层，Life、Behavior、Economy 互相缠绕，Room 直接拿 Desktop 的模块，改一处牵一片。
- 放弃的选项：
  - 只理顺依赖 — 治标，生活相关三块的缠绕不会消失。
  - 先拆成多个 npm 包 — 边界没理清就拆，是把乱搬进多个包，发布和升级更复杂；留作最后一步。
  - 新仓库从零写 — 要同时养两套代码，切换那天风险集中。
  - 并行新目录最后一次性替换 — 中途发不了版。

## 2026-11-16 没有现成替代，上游代码整体复用

- 决定：`vendor/mnemosyne` 作为记忆引擎整体复用，只重新装配接口、身份范围、创建和关闭；`vendor/dsh-pet`、`vendor/dsh-world`、`vendor/feiyu-room-template` 整体保留，按层分配消费它们的适配器。`client.js`、`shared-core.js` 是生成文件，要改就改生成器。
- 为什么：调研（基线 0.1.8，只读）没有找到必须重写的证据；Project AIRI、Open-LLM-VTuber、Replika 都缺长期记忆或 DSH 接入，或者不能自托管和迁移数据，而重构的前提是保留已有数据和 DSH 体系。
- 放弃的选项：重写记忆引擎 — 没有证据表明需要。

## 2026-11-16 重构期间兼容面保持不变

- 决定：包名 `her-world`、Bundle ID、包入口、旧 `00-Core … 70-Voice` 入口、`petX` 服务名、配置项整个重构期间都保留；阶段 4 删除旧入口前，以已安装环境的配置实际不再引用为条件。完整清单见 [architecture.md](architecture.md) 6.1。
- 为什么：保证 DSH 里的更新按钮照常可用，已安装环境能无缝升级。
- 放弃的选项：重构中途改名或删旧入口 — 升级路径无法验证。

## 2026-11-16 回退的边界

- 决定：回退 = 恢复安全备份 + 换回旧版安装包；新版期间新增的聊天、已送达消息、已消耗额度列为不可回退状态。「找回新版期间的聊天」做成一个单独的、可选的恢复步骤，放在 P1 之后。
- 为什么：现有恢复器要求安装包指纹完全一致，并把原生日志恢复成备份时的样子（`scripts/lib/offline-backup.mjs:432`）。
- 放弃的选项：承诺「回退后旧版能看到新版的聊天」 — 与恢复器的实际行为相反。

## 2026-11-16 迁移的幂等以目标状态为准，全局停写才迁移

- 决定：每一步先判断目标状态是否已成立，成立就跳过，并保留原 operation / request ID；迁移由主人显式触发、DSH 停写后执行，和现有备份流程串联。
- 为什么：「先写日志、再改数据、最后标完成」仍有数据已提交而标记没写的窗口。
- 放弃的选项：以完成标记判断；启动时静默自动迁移。

## 2026-11-16 第一次迁移只加版本号和迁移日志

- 决定：阶段 1 发版除存储清单版本号和迁移日志外不改数据格式，只作流程演练，不宣告迁移链路已通过。共享 home 身份记录从 `life.json` 拆到第一层是第一项真实迁移，放在阶段 2（2a）；在此之前 Core 对它的读写作为一条基线例外。
- 为什么：放在 MVP 发版里会让回退更难；跨数据库搬迁要等第一次真正的搬迁才能验证。
- 放弃的选项：阶段 1 就迁移 home 记录。

## 2026-11-16 生活世界：目录合并，经济仍可关闭，旧菜园只作迁移来源

- 决定：`behavior/`、`life/`、`economy/` 合并成第二层一个实例，内部直接调用；经济命令和入口保留「可以关闭」，关闭后权威存档保持原样、不退回旧菜园；旧 `garden.json` 不再作为运行路径，只作尚未采用存档的一次性迁移来源。合并目录不等于合并事务，身体文件和经济数据库仍分开提交。常驻实例推荐由 `25-Behavior` 入口创建。
- 为什么：三块实际是同一件事；已采用 Economy 的存档现在就拒绝退回旧钱包（`behavior/plugin.ts:143`），所以外部行为不变。前提待核实：主人的安装已采用 Economy。
- 放弃的选项：用「消除双份实现」推出钱包不可独立关闭。

## 2026-11-16 控制台、语音和经济待确认请求的定位

- 决定：控制台外观先不动，架构定位现在定：第三层里唯一允许操作别的第三层模块的模块，通过运维操作表操作。语音由第一层 contracts 声明接口，Voice 登记为实现。经济待确认请求先原样导出并备份，再导入核对，最后清除浏览器副本。
- 为什么：同层禁止依赖要和控制台的实际职责不矛盾；能力状态行不能被调用，也没有取消和失效约定；导入和清除的顺序要避免循环。
- 放弃的选项：控制台架构推迟；用能力状态表使用 Voice。

## 2026-11-16 检查脚本用已有的 TypeScript 编译器接口写，并要证明自己抓得到

- 决定：R1–R8 用仓库已有的 TypeScript 编译器接口写，不加新依赖；覆盖率靠「已知违规样例集」证明。现状违规固定成基线，新增违规构建失败。R8（词汇重复）同样按棘轮：旧重复留在基线里只报告，新增重复当场阻断。
- 为什么：复盘显示，只报告的话，历史上的扩张和协议分散几乎都会照常通过；「用了编译器接口」本身不能证明覆盖率。
- 放弃的选项：引入 dependency-cruiser 等新依赖；R8 只报告不阻断。

## 2026-11-16 上下文预算只声明和度量，不强制截断

- 决定：每个上下文段声明预算并报告实际大小，不截断。
- 为什么：强制截断会改变现有行为，违反「这次不加新功能」。
- 放弃的选项：重构中同时上线强制预算。

## 2026-11-16 阶段 1 既是 MVP 又含地基和第一层，用三个里程碑切开

- 决定：阶段 1 分 M1（安全网）、M2、M3，各有完成标准和止损点；第一个评审点在 M1 结束（继续 / 缩小 / 止步），评审前不进入 M2。M1 只做安全网，概念表、会话策略表、上下文段清单在用到它的里程碑之前交付。阶段结束时典型修改对比没有任何改善、主人也觉得代码没更好读，就停下来讨论。
- 为什么：阶段 1 规模大，需要中途止损；纸面表格提前全做完容易过期。
- 放弃的选项：把 M1 单独作为阶段 1、M2 和 M3 作为阶段 2 — MVP 就不再是第一个阶段，和一句话 MVP 对不上。

## 2026-11-16 防乱机制 G1–G9 按推荐加入

- 决定：违规棘轮、方案准入问题、故障家族复盘、范围冻结、自动度量、`AGENTS.md` 一页入口、规则要有案例、阶段末复盘规则、完成标准含真实流程，共 9 条；G1、G2、G3、G9 必须，G5、G6 可后置。详见 [product.md](product.md)。
- 为什么：对 Her World 42 个提交的复盘显示，混乱主要来自范围扩大后拥有者和验收没有跟着收口、局部修好又继续叠下一批；每个模块各自通过不能代替整条流程的验证。
- 放弃的选项：「整个阶段零报警」作为删除规则的理由。

## 2026-11-16 全仓同类问题不开专项

- 决定：全仓扫描发现的另外 15 处同类问题并入对应阶段；`CoreStore` 记录 kind 带类型、错误码单一定义、DSH 原生事件的统一投影三处属于第一层，放进阶段 1。
- 为什么：开专项会扩大范围，并入对应阶段由各自的完成标准验收。
- 放弃的选项：单独开一个清理阶段。

## 2026-11-16 开发期间用合成数据副本，真实副本只在检查点用

- 决定：按真实布局生成不含主人内容的合成副本，日常演练都在它上面跑；真实副本由主人提供位置和隔离环境，只盘点路径和表名、不读内容，只在 M1 盘点和演练、M3、阶段 2、阶段 3 的检查点用。
- 为什么：主人的真实数据只有一份，内容不发给模型服务商。
- 放弃的选项：开发期间直接用真实副本。

## 2026-11-17 仓库文档改用中文

- 决定：仓库文档用中文写；代码、命令、路径、分支名用英文。现有英文文档下次改到时再译。
- 为什么：重构立项的产品、架构、决定文档都是中文，主人读中文更顺；和个人开发规则一致。
- 放弃的选项：把立项文档译成英文 — 工作量大，主人读起来更费劲。

## 2026-11-17 架构检查不扫 vendor 里的生成源，R8 条目按位置记身份

- 决定：生成文件不扫描，它们的生成源里只扫生成脚本和 `src/` 里的文件，`vendor/` 里的生成源跳过，由 `check:arch -- --report` 单独列出（收窄拍板点 7）。R8 重复关系的基线身份是「规则 + 双方文件 + 双方函数路径 + 本方形状」，不含集合取值、表达式正文和重复/子集关系。
- 为什么：vendor 是上游代码，扫进来会产生无法处理的词表重复和误报，同步上游时门禁会卡死，而且只减不增的基线没有正当出路；同样，身份里带取值，改一句标签文案或给已有集合加一个值也会被永久挡住。
- 放弃的选项：照原样扫描 vendor 生成源；R8 身份包含取值或关系。

## 2026-11-17 迁移和盘点命令只输出固定原因代码，不输出原始错误

- 决定：`scripts/migrate/` 的迁移和盘点命令失败时，只输出一个固定原因代码加一句固定说明（例如 `dsh-running`、`lock-held`、`backup-invalid`、`journal-exists`），代码在抛错处按错误类型分类，退出码非 0；盘点输出的根目录用 `sessions-1`、`cache-1` 这类编号，不带工作区 ID 等绑定值。
- 为什么：真实副本检查点由主人运行，Agent 只看程序输出；现有校验器的断言信息里可能带身份或内容，不能原样打印。但一句笼统的拒绝提示又分不清 DSH 没关、锁被占和备份损坏。
- 放弃的选项：吞掉错误只打印一句笼统提示；按原始错误信息的文字匹配分类。

## 2026-11-18 M1 评审：继续完整重写，M2 完成后复测再决定 M3

- 决定：选 A，进入 M2。M2 完成后先复测第 4、第 5 类典型修改（新增工具、新增输入来源）实际要动的文件数和层数，没有明显下降就在 M3 开始前转为 B（缩小）。「明显下降」的门槛见 [product.md「典型修改前后对比」](product.md#典型修改前后对比)。
- 为什么：现有 81 条违规里 Core 占 30 条，而 M2 是几张登记表（能力状态、初始化、来源适配、会话策略），目标可以按数字核对；它直接对应最费事的第 4、5 类修改。行为清单、检查棘轮、迁移和回退已在真实副本上演练通过，动第一层的风险可控。M3 工作量大（投影表、组装契约、发版），所以放在复测之后再定。
- 放弃的选项：B 缩小，跳过第一层的大改，直接做第二层合并和概念统一（四个故障家族大多在第二、三层，但 Core 的违规和写死的对应关系会一直留着）；C 止步（没有出现止损信号）。
